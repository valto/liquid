# Documentation as Executable Foundations

**Definition.** Shared terminology, capability requirements and guidance preserve meaning while implementations and operational choices evolve.

Documentation describes purpose, boundaries, accepted outcomes, terminology and relevant unknowns. Agents can use these foundations to interpret needs without requiring every implementation to be designed in advance.

Guidance is not automatically permission. A capability's documentation and the actor's actual authority answer related but distinct questions. Contradictions and unresolved meanings should remain visible.

## Maintain meaningful scope

Minimum Logical Element (MLE) is a scope discipline: a unit retains enough context to be understood across relevant perspectives. Capability Requirements Documents (CRDs) document meaningful capabilities independently of one endpoint, screen or realization.

## Verify the foundation

Test whether different participants interpret a capability consistently, whether accepted outcomes can be checked, and whether revisions preserve attributable history. Documentation helps govern adaptation without guaranteeing correctness merely by existing.


## Document learning and implementation separately

Retain the basis of an assessment: evidence, assumptions, confidence, dependencies, scope and last review. A review charter can describe purpose, depth, cadence, triggers and authority. These logical records make understanding reusable and revisable without requiring one storage schema.

Capability requirements, Skill instructions, agent orchestration and executable logic describe different concerns. The proposed [Reasoning Compilation](https://valto.github.io/liquid/concepts/reasoning-compilation/) capability converts formally checkable portions into validated structures, preserving their assumptions and invalidation conditions. Its documentation does not establish that a compiler or Skill is installed.
