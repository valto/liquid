# Liquid Software for product and engineering

Liquid Software separates what a capability means from the code, interface or agent that currently realizes it. For product people, architects and developers, the main question is **what must remain stable so implementation can change without changing the promise?**

The resource proposes durable semantics and evidence, with interfaces and execution paths selected around actual needs. Stable software remains a valid result of that selection.

## Define a meaningful capability before choosing a component

A complete commitments briefing has a beneficiary, purpose, acceptance criteria and boundaries. A database table, screen or function may support it without being an independent capability. Capability documentation can retain this meaning across realizations; it does not make each code fragment a meaningful unit.

Minimum Logical Element is the related scope discipline, and CRD offers a capability-centered documentation approach. These are related frameworks with their own definitions. A technical description and the actor's actual permission remain separate inputs to execution.

## Start with languages, formats and shared meaning

A human question and a structured request can express the same need while requiring different response representations. The user contributes purpose and desired view; the receiver contributes supported meaning and available evidence; the information principal governs use and disclosure.

Schemas can be inferred, generated or negotiated when they supply needed precision. The proposal does not require permanently handwritten schemas for every future question. Equally, familiar syntax alone does not establish a contract. The API research draft distinguishes dynamic schema preparation from validation and execution under the selected GraphQL specification; a claimed conforming implementation still needs its applicable structure and rules.

## Compose an implementation around its contracts

The expanded economics paper's illustrative procurement capability combines reasoning, field extraction, policy rules, exact calculation, an authorized existing API and an attributable evidence record. Different operations can use different realizations while serving one accepted outcome.

A replacement model must still meet its extraction contract. A generated UI must still communicate uncertainty and support its intended user. Replacing an implementation should preserve identities, accepted facts, authority and recovery requirements where those are commitments of the capability.

## Specialize where evidence supports it

The proposed Reasoning Compilation Skill identifies formally checkable portions, creates a candidate and validates it with independent tests, invariants and adverse cases. Preserve assumptions and invalidation conditions. Determinism does not establish truth or freshness. This is a proposed capability, not an installed compiler.

A candidate can be evaluated beside the active realization without duplicate side effects. Release, adoption and retirement are distinct. Focused, expert, hybrid and agent-used experiences can share a capability; their modes are contextual choices. Preserve compatibility and account for parallel support, coordination and assurance costs.

## A bounded engineering evaluation

Choose one capability and keep its current accepted baseline. Specify representations, permissions, unresolved meanings and failure responses. Compare candidate realizations on the same source evidence and acceptance criteria, including exceptions, permission denial and restoration after a failed change.

The reference architecture describes concerns and boundaries to test. It is not a deployed platform, a universal protocol, or evidence that every proposed interaction can already be fulfilled.

## A short reading path

1. [Documentation as Executable Foundations](https://valto.github.io/liquid/concepts/documentation-as-foundations/). Start with purpose, terminology and meaningful scope.
2. [Beyond Predefined APIs — Research Draft 09](https://valto.github.io/liquid/whitepapers/drafts/09-beyond-predefined-apis/). Examine languages, schemas and agreements.
3. [Reasoning Compilation](https://valto.github.io/liquid/concepts/reasoning-compilation/). Read validation, assumptions and revalidation of exact portions.
4. [Parallel Realizations](https://valto.github.io/liquid/concepts/parallel-realizations/). Separate candidate testing, release, adoption and retirement.
5. [Continuous Intelligence, Adaptive Evolution, and Stable Experience](https://valto.github.io/liquid/whitepapers/continuous-intelligence/). Read chapters 5–7 and scenario B with the diagrams.

## Questions to explore

- Which semantics and commitments belong to the capability, and which details belong to this realization?
- What needs a fixed contract, and what can be resolved contextually?
- Which parts deserve exact code, and which require interpretation?
- What invalidates compiled logic, and how will parallel versions preserve compatibility and recovery?
